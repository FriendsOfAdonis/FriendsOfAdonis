AdonisJS RBAC is a role-based access control system for AdonisJS. You declare every permission of your application once, group them into roles, assign roles to users, and authorize with the Bouncer API you already use.

```ts title="start/rbac.ts"
import { definePermissions, defineRoles } from "@foadonis/rbac";

export const permissions = definePermissions({
  article: {
    create: true,
    publish: "Publish articles",
    delete: "Delete articles",
  },
  comment: {
    moderate: "Moderate comments",
  },
});

export const roles = defineRoles(permissions, {
  writer: { permissions: ["article.create"] },
  editor: { permissions: ["article.*", "comment.moderate"] },
});
```

```ts title="app/controllers/articles_controller.ts"
import type { HttpContext } from "@adonisjs/core/http";

export default class ArticlesController {
  async publish({ bouncer }: HttpContext) {
    await bouncer.authorize("article.publish");

    // The user holds a role that grants article.publish
  }
}
```

## When to use it

[Bouncer](https://docs.adonisjs.com/guides/security/authorization) asks you to write one function per ability. That fits rules that depend on a resource, such as "users can edit their own articles". It gets repetitive for static rules, such as "editors can publish articles", where the answer depends only on the role of the user.

RBAC covers the static rules. It generates one Bouncer ability per permission key, so `bouncer.authorize("article.publish")` sits next to your hand-written abilities and policies. Keep ownership and conditional checks in Bouncer abilities and policies.

## Features

- **Typed keys.** Permission keys and role names are inferred from the definition. A typo in `bouncer.authorize`, `assignRole` or `hasPermission` fails the build.
- **Roles in code.** Roles live next to the permissions and ship with your deployments. Users store role names in a JSON column, with no extra table. Database roles remain available when an admin needs to edit them at runtime.
- **Nested namespaces.** Group keys at any depth, such as `admin.user.ban`, and grant a whole subtree with `admin.*`.
- **Validated writes.** `assignRole`, `givePermission` and `syncPermissions` reject unknown values at runtime, so input from an admin form cannot store garbage.
- **Aliases and inactive keys.** Rename a key or a namespace without rewriting stored data, or switch a key off without deleting it.
- **Token scoping.** Narrow a check to the abilities of an access token. The default `["*"]` token keeps every permission.
- **One load per request.** The generated abilities load the grants of a user once, however many checks you run.
- **Teams.** Any Lucid model can hold roles, so a team member can have different roles in each team.
