Roles cover most needs. Sometimes one user needs a permission their role does not grant, such as a writer who also moderates comments. Rather than creating a role for one person, give the permission to the user directly.

## The permissions column

`withPermissions` works on any Lucid model, including `User`. It stores grants in a JSON `permissions` column. The migration generated by `node ace configure` already adds a nullable `permissions` column to the `users` table, so existing users stay valid. The mixin reads `null` as an empty list and writes `[]` on create.

If you skipped that migration, add the column yourself with `table.json("permissions").nullable()`.

## Apply the mixin

Compose `withPermissions` with the mixin that holds roles, either `withRoles` for [roles in code](/docs/rbac/roles) or `withRoleModel` for [roles in the database](/docs/rbac/roles#store-roles-in-the-database). The order does not matter.

```ts title="app/models/user.ts"
import { compose } from "@adonisjs/core/helpers";
import { BaseModel } from "@adonisjs/lucid/orm";
import { withPermissions, withRoles } from "@foadonis/rbac";
import { permissions, roles } from "#start/rbac";

export default class User extends compose(
  BaseModel,
  withRoles(roles),
  withPermissions(permissions)
) {
  // ...your existing columns
}
```

The mixin registers the `permissions` column itself. Do not declare it on the model.

## Give, sync and revoke

The methods validate their input, save the model right away, and accept keys and [wildcards](/docs/rbac/defining-permissions#wildcards).

```ts
await user.givePermission("comment.moderate");
await user.givePermissions(["comment.moderate", "admin.user.*"]);

await user.syncPermissions(["comment.moderate"]);

await user.revokePermission("comment.moderate");
await user.revokePermissions(["admin.user.*"]);
```

- `givePermission` and `givePermissions` add grants. Giving a grant the user already holds does nothing.
- `syncPermissions` replaces every grant stored on the user.
- `revokePermission` and `revokePermissions` remove grants and their stored [aliases](/docs/rbac/defining-permissions#aliases). Revoking a grant the user does not hold does nothing.

Revoking a key does not narrow a wildcard. If the user holds `admin.user.*`, revoking `admin.user.ban` leaves `admin.user.*` in place. Revoke `admin.user.*` and give the remaining keys instead.

Every method throws `E_UNKNOWN_PERMISSION` when a value is neither a defined key nor a valid wildcard.

These methods only touch the grants stored on the user. They never change the roles of the user or the grants of those roles.

## Combined permissions

`getPermissions`, `hasPermission` and the Bouncer abilities use the union of the direct grants and the grants of every role.

```ts
// The writer role grants article.create
// The user also holds comment.moderate directly

await user.getPermissions();
// ["article.create", "comment.moderate"]
```

The package has no deny rules. A direct grant can add permissions to a user, but cannot remove a permission that a role grants.
