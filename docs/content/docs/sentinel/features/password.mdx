A forgotten password is recovered with a single-use token. You email it to the user as a link, they open it, type a new password and are signed back in.

Sentinel takes care of the passwords and the tokens: it hashes the passwords with the default hasher of `config/hash.ts`, verifies the credentials at login, and issues reset tokens it accepts exactly once. Sending the email and rendering the form stay in your hands, so the flow fits any mail setup and any frontend.

## Getting started

Sentinel must be installed and configured as described in the [installation guide](/docs/sentinel/getting-started), with the `sentinel_tokens` table migrated. The examples below use the session guard of `@adonisjs/auth` and `@adonisjs/mail`: adapt them to the guard and the mailer of your application.

<div className="fd-steps [&_h3]:fd-step">

### Prepare the model

Compose the `withPassword` mixin, exported by `@foadonis/sentinel/password`, into the model your users sign in with. The mixin hashes the `password` column before save whenever it changes, adds `generatePasswordResetToken`, `invalidatePasswordResetTokens`, `verifyPassword`, `validatePassword` and `updatePassword` to the instances, and the static `verifyCredentials`, `verifyPasswordResetToken` and `resetPassword` methods to the model:

```ts title="app/models/user.ts"
import { compose } from "@adonisjs/core/helpers";
import { BaseModel, column } from "@adonisjs/lucid/orm";
import { withPassword } from "@foadonis/sentinel/password";

export default class User extends compose(BaseModel, withPassword()) {
  @column({ isPrimary: true })
  declare id: number;

  @column()
  declare email: string;

  @column({ serializeAs: null })
  declare password: string;
}
```

<Callout type="warn">
  `withPassword` is a drop-in replacement for `withAuthFinder` from
  `@adonisjs/auth`, with the same hook, methods and `E_INVALID_CREDENTIALS`
  exception: if the model composes it, remove it. Never compose both, the
  passwords would be hashed twice. Unlike `withAuthFinder`, the hasher is not an
  argument: passwords are hashed with the default hasher of `config/hash.ts`.
</Callout>

### Send a reset link

The address comes from a forgot-password form of yours, submitted to the `send` action. Generate a token for the user and email it as a link to the page holding the reset form. The token is wrapped in a `Secret`, so it stays out of the logs: call `release` to read it. The example builds the URL with the `urlFor` helper of AdonisJS, from the name given to the form route in the next step, and `prefixUrl` makes it absolute:

```ts title="app/controllers/password_reset_controller.ts"
import type { HttpContext } from "@adonisjs/core/http";
import { urlFor } from "@adonisjs/core/services/url_builder";
import mail from "@adonisjs/mail/services/main";
import env from "#start/env";
import User from "#models/user";

export default class PasswordResetController {
  async send({ request, response, session }: HttpContext) {
    const user = await User.findBy("email", request.input("email"));

    if (user) {
      const token = await user.generatePasswordResetToken();

      const url = urlFor("password.reset", undefined, {
        qs: { token: token.release() },
        prefixUrl: env.get("APP_URL"),
      });

      await mail.sendLater((message) => {
        message
          .to(user.email)
          .subject("Reset your password")
          .htmlView("emails/password_reset", { url });
      });
    }

    session.flash(
      "success",
      "If an account exists for this address, a reset link is on its way.",
    );
    return response.redirect().back();
  }
}
```

`APP_URL` is not part of the default environment schema: declare it as a required string in `start/env.ts` if your application does not define it yet.

<Callout type="warn">
  Respond the same way whether or not the address is known. Telling the visitor
  that no account exists lets anyone enumerate your users.
</Callout>

### Reset the password

The link opens the page rendering the reset form: have it hold the token in a hidden field, read from the query string with `request.input("token")`, next to the new password field, and submit both to the `reset` action. The action hands the token and the password to the static `resetPassword` method and opens the session with the user it returns:

```ts title="app/controllers/password_reset_controller.ts"
export default class PasswordResetController {
  // ...

  async reset({ request, response, auth }: HttpContext) {
    const [user] = await User.resetPassword(
      request.input("token"),
      request.input("password"),
    );

    await auth.use("web").login(user);

    return response.redirect("/dashboard");
  }
}
```

```ts title="start/routes.ts"
import router from "@adonisjs/core/services/router";
const PasswordResetController = () =>
  import("#controllers/password_reset_controller");

router.on("/forgot-password").render("pages/forgot_password");
router.post("/forgot-password", [PasswordResetController, "send"]);
router
  .on("/reset-password")
  .render("pages/reset_password")
  .as("password.reset");
router.post("/reset-password", [PasswordResetController, "reset"]);
```

Validate the new password before resetting it, with a VineJS schema enforcing your length rules and a confirmation field, the way you validate any form.

</div>

The first verification consumes the token: submitting the form again fails with an `E_INVALID_TOKEN` exception, exactly like an expired link does, and a successful reset invalidates every other pending reset token of the user. See [Handling invalid tokens](#handling-invalid-tokens) to turn the exception into a friendly message.

<Callout type="warn">
  Do not verify the token when rendering the form: a verification consumes it,
  so the submission that follows would fail. Render the form as is and let a bad
  token surface on submit.
</Callout>

## Verifying credentials

The same mixin signs your users in. The static `verifyCredentials` method looks the user up by email, verifies the password and returns the user:

```ts title="app/controllers/session_controller.ts"
import type { HttpContext } from "@adonisjs/core/http";
import User from "#models/user";

export default class SessionController {
  async store({ request, response, auth }: HttpContext) {
    const { email, password } = request.only(["email", "password"]);

    const user = await User.verifyCredentials(email, password);
    await auth.use("web").login(user);

    return response.redirect("/dashboard");
  }
}
```

An unknown email and a wrong password both throw the `E_INVALID_CREDENTIALS` exception, and take the same time to do so, so that neither the response nor its timing tells an attacker which one it was. The exception carries a `400` status and renders like the one of `@adonisjs/auth`: it flashes the error and redirects back when the request comes from a form, and returns an error object on JSON requests. Its message is translated under the `errors.E_INVALID_CREDENTIALS` key when `@adonisjs/i18n` is configured.

The columns the user is looked up by, `["email"]` by default, are set by the `uids` option of the mixin: `verifyCredentials` matches its first argument against each of them, so a single field on the login form serves them all. See [Mixin configuration](#mixin-configuration):

```ts title="app/models/user.ts"
export default class User extends compose(
  BaseModel,
  withPassword({ uids: ["email", "username"] }),
) {
  // ...
}
```

A successful login also rewrites the stored hash when it was made with outdated options, after you strengthen `config/hash.ts` for example, so the hashes upgrade as your users sign in. Set `rehashOnVerify: false` on the mixin to keep the hashes untouched.

## Changing the password

A signed-in user changes their password from a settings form holding two fields: the current password and the new one. `updatePassword` verifies the current password, saves the new one and invalidates every pending reset token, since a pending token is a way into the account:

```ts title="app/controllers/settings_controller.ts"
import type { HttpContext } from "@adonisjs/core/http";

export default class SettingsController {
  async updatePassword({ request, response, auth, session }: HttpContext) {
    const { currentPassword, password } = request.only([
      "currentPassword",
      "password",
    ]);

    const user = auth.getUserOrFail();
    await user.updatePassword(currentPassword, password);

    session.flash("success", "Your password has been updated.");
    return response.redirect().back();
  }
}
```

A wrong current password throws an `E_INVALID_PASSWORD` exception with a `400` status. To report it like a validation failure instead, call `validatePassword` first: it throws an error shaped like a VineJS failure on the `currentPassword` field, with a `422` status, so the exception handler renders it like any form error, inline error message included:

```ts
const user = auth.getUserOrFail();
await user.validatePassword(currentPassword);
await user.updatePassword(currentPassword, password);
```

`validatePassword` also fits any flow where the user confirms their password before something sensitive, deleting the account for example. Its second argument names the field the error is reported on:

```ts title="app/controllers/account_controller.ts"
export default class AccountController {
  async destroy({ request, response, auth }: HttpContext) {
    const user = auth.getUserOrFail();
    await user.validatePassword(request.input("password"), "password");

    await user.delete();
    return response.redirect("/");
  }
}
```

Underneath both sits `verifyPassword`, which returns a boolean instead of throwing. Assigning the `password` column and saving also works, the hook hashes it, but it skips the current-password check and leaves the pending reset tokens valid: reach for it only when you are setting a password outside an authenticated flow, when seeding users for example.

## Configuration

### Global configuration

The `password` key of `config/sentinel.ts` accepts a single option, and the whole key can be left out:

- `expiresIn`: The lifetime of the reset tokens, in seconds or as a duration string like `"30m"` or `"1h"`. Defaults to `"1h"`.

```ts title="config/sentinel.ts"
import { defineConfig, tokens } from "@foadonis/sentinel";

const sentinelConfig = defineConfig({
  tokens: tokens.lucid(),
  password: {
    expiresIn: "30m",
  },
});

export default sentinelConfig;
```

<Callout>
  Reset tokens are persisted by the token provider configured under `tokens`, in
  the `sentinel_tokens` table shared with the magic link and OTP modules. See
  the [installation guide](/docs/sentinel/getting-started) for the migration.
</Callout>

### Mixin configuration

The options given to `withPassword` configure how the model authenticates:

- `uids`: The columns `verifyCredentials` looks the user up by. Defaults to `["email"]`.
- `passwordColumnName`: The column holding the hashed password. Defaults to `"password"`.
- `rehashOnVerify`: Whether a successful `verifyCredentials` rewrites the hashes made with outdated options. Defaults to `true`.

They also set the defaults of every reset token the model generates:

- `expiresIn`: The lifetime of the tokens, as in the global configuration.
- `purpose`: The purpose of the tokens. It is also the purpose `verifyPasswordResetToken`, `resetPassword` and `invalidatePasswordResetTokens` use by default, see [Purposes](#purposes).
- `metadata`: Data attached to every token, see [Metadata](#metadata).

```ts title="app/models/user.ts"
export default class User extends compose(
  BaseModel,
  withPassword({ uids: ["email", "username"], expiresIn: "30m" }),
) {
  // ...
}
```

<Callout type="warn">
  Tokens are stored by primary key, not by model. When several models compose
  the mixin, give each one its own purpose: a token generated for one model
  could otherwise be verified as another. The revocation following a password
  change ignores purposes though, so it also hits the tokens of another model
  sharing the same key value.
</Callout>

<Callout>
  Options given when generating a token take precedence over the defaults of
  the mixin, which take precedence over `config/sentinel.ts`. `metadata` is
  replaced as a whole, not merged.
</Callout>

### Per-token options

`generatePasswordResetToken` accepts `expiresIn`, `purpose` and `metadata` for a single token:

```ts
const token = await user.generatePasswordResetToken({ expiresIn: "10m" });
```

The token comes back wrapped in a `Secret`, so call `release` to read it. `verifyPasswordResetToken` and `resetPassword` accept a string or a `Secret`, along with a `purpose` option.

## Handling invalid tokens

`resetPassword` and `verifyPasswordResetToken` throw an `E_INVALID_TOKEN` exception, with a `401` status, when the token is unknown, expired, already used, or created for another [purpose](#purposes). The mixin also throws it when the user of the token no longer exists. Catch it in the action, or in the global exception handler:

```ts title="app/exceptions/handler.ts"
import { ExceptionHandler, type HttpContext } from "@adonisjs/core/http";
import { errors } from "@foadonis/sentinel";

export default class HttpExceptionHandler extends ExceptionHandler {
  async handle(error: unknown, ctx: HttpContext) {
    if (
      error instanceof errors.E_INVALID_TOKEN &&
      error.kind === "password_reset"
    ) {
      ctx.session.flash(
        "error",
        "This reset link is invalid or has expired. Request a new one.",
      );
      return ctx.response.redirect("/forgot-password");
    }

    return super.handle(error, ctx);
  }
}
```

The magic link and OTP modules throw the same exception, hence the check on its `kind` property. Its `purpose` property carries the purpose the token was verified with.

## Purposes

When reset tokens serve more than one flow, tag each token with a purpose. A token is only accepted with the purpose it was created for. A typical second flow is an invitation: a freshly created user receives a link to set their first password, valid for longer than a reset. Such a user starts without a password, so declare the column nullable on the model. When sending the link:

```ts
const token = await user.generatePasswordResetToken({
  purpose: "invitation",
  expiresIn: "7d",
});
```

When the user submits the form:

```ts
const [user] = await User.resetPassword(
  request.input("token"),
  request.input("password"),
  { purpose: "invitation" },
);
```

Without purposes, both flows would draw from the same pool of tokens: an invitation link could be replayed against the forgot-password form, and the other way around.

A purpose given to the mixin is the default of `generatePasswordResetToken`, `verifyPasswordResetToken`, `resetPassword` and `invalidatePasswordResetTokens`, so a model dedicated to one flow never needs the option. To reach the tokens without purpose on such a model, pass `purpose: undefined` explicitly: the mixin only falls back to its default when the option is left out.

## Metadata

Attach arbitrary data to a token and get it back from the verification, as the second element of the tuple `resetPassword` and `verifyPasswordResetToken` return. The data is stored next to the token, not in the link, so the user cannot tamper with it. A redirect target is the typical use. Extending the actions of the [Getting started](#getting-started) guide:

```ts title="app/controllers/password_reset_controller.ts"
export default class PasswordResetController {
  async send({ request, response, session }: HttpContext) {
    const redirect = request.input("redirect", "/dashboard");
    // ...
    const token = await user.generatePasswordResetToken({
      metadata: { redirect },
    });
    // ...
  }

  async reset({ request, response, auth }: HttpContext) {
    const [user, metadata] = await User.resetPassword(
      request.input("token"),
      request.input("password"),
    );

    await auth.use("web").login(user);

    return response.redirect(
      typeof metadata?.redirect === "string" ? metadata.redirect : "/dashboard",
    );
  }
}
```

`metadata` is typed `Record<string, unknown> | null`, `null` when the token was generated without metadata, so narrow the values before using them.

<Callout type="warn">
  Metadata is trusted at verification time, so validate it when you store it. In
  the example above, accept `redirect` only when it is a path of your
  application, starting with a single `/`, otherwise the link becomes an open
  redirect.
</Callout>

## Invalidating pending tokens

Every token generated for a user stays valid until it is used or expires. `updatePassword` and `resetPassword` already invalidate all of them, whatever their purpose, once the new password is saved. Call `invalidatePasswordResetTokens` to revoke the pending ones yourself, when the user changes their email address for example, or to make sure a single link is pending at a time:

```ts
await user.invalidatePasswordResetTokens();
const token = await user.generatePasswordResetToken();
```

With this pattern, a user who requested two resets and opens the older link gets an invalid token error.

The revocation is scoped to one purpose: the one given with the `purpose` option, otherwise the default one of the mixin, otherwise the tokens created without purpose. A model using several purposes revokes them one call at a time, and `purpose: undefined` reaches the tokens without purpose on a model with a default, see [Purposes](#purposes). The magic link and OTP tokens of the user are never affected.

```ts
await user.invalidatePasswordResetTokens({ purpose: "invitation" });
```

## Using the manager directly

The mixin is a thin layer over the `PasswordManager`, the default export of `@foadonis/sentinel/services/password`. Reach for the manager when the subject of the tokens does not compose the mixin. Inject it wherever the container constructs your classes, or import the service when you are outside a DI context:

```ts title="app/services/invitation_service.ts"
import { inject } from "@adonisjs/core";
import { PasswordManager } from "@foadonis/sentinel/password";

@inject()
export default class InvitationService {
  constructor(protected password: PasswordManager) {}
}
```

```ts
import password from "@foadonis/sentinel/services/password";
```

The manager exposes the token operations of the mixin, `generatePasswordResetToken`, `verifyPasswordResetToken` and `invalidatePasswordResetTokens`, with the primary key of the subject as the first argument:

```ts
const token = await password.generatePasswordResetToken(member.id, {
  purpose: "invitation",
});
```

`verifyPasswordResetToken` verifies and consumes the token exactly like the mixin does, but returns the persisted token instead of a model: a `SentinelToken` carrying the `tokenableId`, `purpose`, `metadata` and `expiresAt` of the reset. Finding the subject and saving the new password are up to you:

```ts
const verified = await password.verifyPasswordResetToken(
  request.input("token"),
);
const member = await Member.findOrFail(verified.tokenableId);
```

It also exposes `invalidateAllPasswordResetTokens`, which ignores purposes: it is what the mixin calls once a password is set. And underneath everything sit the hashing primitives the mixin builds on, `hashPassword`, `verifyPassword` and `needsRehash`, bound to the default hasher of `config/hash.ts`.

<Callout>
  The mixin resolves the manager through the static `$passwordManager` getter of
  the model, on every access and never when the model is defined, so the model
  can be imported before the application has booted. Pass a `manager` option,
  an instance or a function returning one, when you construct the manager
  yourself, in tests for example, or override the getter on the model to give
  it a manager of its own.
</Callout>

## Under the hood

- Passwords are hashed by the `beforeSave` hook with the default hasher of `config/hash.ts`, so a plain password never reaches the database.
- `verifyCredentials` hashes the password even when no user matches the uid, so a missing user takes as long as a wrong password.
- The reset token is made of 40 random characters followed by their CRC32 checksum. Only its SHA-256 hash is persisted, so a leaked database does not leak the pending resets.
- The value is returned once, wrapped in a `Secret`, and never stored.
- A token is consumed atomically: two concurrent verifications of the same token cannot both succeed.
- Expired and consumed tokens are deleted as soon as they are seen.
